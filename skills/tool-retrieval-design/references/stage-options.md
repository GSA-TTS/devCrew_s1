# Stage options for the design table

One section per row of the design table, in table order. Each record gives a Choice, Use when (the condition to name in the Why it fits column), Do not use when, and Limits (copy into the Limits column). Where a record has no Do not use when, none is stated.

## 1. Catalog and index

- Choice: an authoritative, versioned tool registry; the search index is a derived view. Use when: any production catalog that is large, mutable, multi-tenant or consequential (a static, read-only prototype with fewer than roughly a dozen tools may need only a versioned in-process catalog and structured logs). Limits: each tool version has a canonical ID independent of display name; index records point to immutable catalog versions, and the definition is fetched by ID and its digest verified after retrieval. Registry fields: canonical ID, namespace, version and digest; owner and lifecycle state; positive-use description, negative-use boundary and known confusing neighbours; input and output schemas; side-effect class, approval class and required scopes; tenant, region, environment and model compatibility; health, latency, cost, deprecation and revocation state; dependency edges.
- Choice: names and descriptions. Use when: always. Limits: stable, specific, action-oriented names under a namespace that expresses owner or domain; two servers never publish the same unqualified name into one candidate set; descriptions state positive and negative boundaries, data source, preconditions, side effects and output, and are reviewed, signed or hash-pinned and length-bounded. Treat names, descriptions, schemas, examples, server instructions and synthetic queries as untrusted until reviewed: authenticate publishers, keep semantic diffs, normalize Unicode, reject hidden or executable content and any text about policy, secrets, other tools, system prompts or unrelated destinations, cap scores or normalize fields so repeated keywords cannot dominate, and place third-party descriptions in context delimited and labelled as untrusted capability metadata, not in the system instruction.
- Choice: several search documents per tool rather than one blob. Use when: always; add documentation chunks only when long documentation holds distinctions missing from the descriptor, and a graph document only for composite tasks. Documents: identity (name, aliases, namespace, operation identifiers; favour lexical retrieval), capability (positive use, outcome, negative boundary), input contract (parameter names, units, formats, required status, enumerations), examples (two to five reviewed user-intent examples, and difficult non-examples separately), documentation chunks (each mapped to one tool version), synthetic queries, graph summary (actual edges kept in a structured graph). Do not use when: the content is credentials, tenant secrets, live customer data, raw tokens, private endpoints or mutable health values (keep policy and health as filters from authoritative state). Limits: no unlimited concatenation into one vector; keep field-level provenance so fields can be fused late.
- Choice: synthetic query generation loop. Use when: a new tool has sparse documentation, paraphrase recall is weak, or production queries show vocabulary the catalog lacks. Limits: generate from the exact tool definition, positive and negative uses and confusing neighbours; reject queries needing an undeclared capability, permission, parameter or data source; an independent rule set or reviewer labels each one positive, negative, ambiguous or prerequisite-only; store accepted queries under their own version without overwriting human examples; rebuild and run the held-out suite; exit when recall improves without exceeding precision, security and collision thresholds; stop after three generation-revision rounds for one tool, then rewrite or split the tool contract.

## 2. Eligibility filter

- Choice: deterministic metadata filter before lexical or vector search. Use when: always. Filter on: tenant, user, role, delegated scopes, purpose and resource constraints; environment, region, residency, protocol, model and schema compatibility; lifecycle, release channel, revocation, health and maintenance state; risk ceiling, side-effect class, approval availability, cost ceiling, latency budget and workflow stage. Limits: identity, tenant, scopes, risk ceiling and environment come from trusted state, not from the model; record counts and reason codes for every exclusion; never retrieve globally and remove unauthorized candidates only after logging, reranking or showing them to a model; when no eligible tool class can satisfy the goal, exit as capability unavailable without searching the global catalog.
- Choice: filter enforced inside the search query. Use when: the search backend can enforce tenant and entitlement filters in the query. Do not use when: it cannot; then build a physically or cryptographically isolated index for that boundary.
- Choice: tenant boundary, chosen by risk. Options: a physical index or collection per tenant (strongest isolation); a namespace or shard per tenant when the backend guarantees filter enforcement; a shared index with mandatory tenant payload filters, only for lower-risk data and only after adversarial isolation tests. Limits: the same boundary applies to lexical and vector indexes, graph edges, caches, traces, evaluation exports and backups.
- Choice: host or protocol lists that vary by authorization (an MCP server may vary its tool list per request). Limits: still intersect the returned list with the host's own policy; never leak tool names, descriptions, existence or scores to a caller not permitted to know them.

## 3. Query construction

- Choice: raw user turn. Use when: the turn is short, explicit and self-contained (keeps wording for exact matching). Do not use when: alone, for pronouns, ellipsis, corrections, or intent stated earlier.
- Choice: conversation-aware query. Use when: the turn depends on prior constraints or artifacts. Limits: a bounded summary with only the facts needed to identify capability, each marked by source and trust; not the whole transcript.
- Choice: rewritten query. Use when: the request needs normalizing into action, object, inputs, outputs, constraints and exclusions (a deterministic template or small model). Limits: at most one normalized rewrite by default; it adds no capability, permission, destination or intent; keep the raw query hash and log the rewrite; if raw and rewritten retrieval disagree materially, keep candidates from both or ask for clarification.
- Choice: capability hypothesis. Use when: no current tool obviously fits; the model describes the operation and parameter semantics without naming a presumed tool. Limits: it is one more query branch, validated against user intent; it does not decide authorization.
- Choice: multi-query expansion. Use when: terminology is ambiguous or the catalog spans vendors and domains. Limits: two to four distinct variants (raw wording, normalized intent, exact identifiers, capability hypothesis), retrieved independently, fused and deduplicated by canonical ID; one expansion round unless the miss-recovery loop authorizes another.
- Choice: per-subgoal and iterative retrieval. Use when: a compound request has several outcome-bearing subgoals, or later tool needs depend on earlier outputs. Limits: one query per unresolved subgoal, union the candidates, add only validated dependency neighbours; retrieve again after the state changes instead of revealing every downstream tool in advance.
- All modes: remove secrets and unauthorized resource details before embedding or logging.

## 4. Retrieval

- Choice: lexical (BM25 or similar). Use when: queries contain tool names, aliases, parameter names, identifiers or error codes; short technical queries; as a transparent baseline and hybrid branch; when embedding service or privacy rules rule out dense inference. Do not use when: alone, if user language differs from the documentation, synonyms dominate, or the capability must be inferred from an outcome.
- Choice: dense embedding. Use when: paraphrases, outcome-oriented requests, supported multilingual matching, low lexical overlap. Limits: only when the model is licensed for the data class, query and document formatting match the model's requirements, the same version, dimensions, normalization and distance are used at build and query time, a migration plan exists, and recall is measured on the actual catalog including new and rare tools.
- Choice: hybrid, lexical and dense in parallel over the same eligible snapshot, fused with reciprocal rank fusion. Use when: exact names and paraphrases both occur, the catalog is heterogeneous, or one retriever's failure modes are unacceptable. Do not use when: one method already meets held-out recall and latency goals. Limits: tune each branch's depth and fusion parameters on labels; do not compare cosine and BM25 scores directly without calibration.
- Choice: hierarchy or namespace routing (route to namespaces, then search within). Use when: stable domains with clear boundaries. Do not use when: tools routinely span domains, categories are mutable or political, or root errors cannot be recovered. Limits: keep an escape path to adjacent namespaces; evaluate namespace recall and within-namespace recall; a taxonomy is not an entitlement system.
- Choice: dependency-aware graph expansion. Use when: tasks need prerequisites, outputs that feed later inputs, authentication setup, lookup before mutation, or companion verification tools. Limits: expand only typed edges consistent with the task, not every neighbour; label edge type, direction, version compatibility, required state and risk; policy-filter every expanded node.
- Choice: learned or fine-tuned retriever. Use when: a stable volume of high-quality query-to-tool labels exists and generic hybrid retrieval has plateaued. Limits: include hard negatives, no-tool cases, unseen-tool splits and multi-tool completeness; hold out entire tools, namespaces, owners and future time windows; do not memorize tool IDs, stale descriptions or tenant secrets.
- Delivery complements: progressive disclosure (compact names or namespace summaries first, full schemas on demand; keep a small always-on core; verify that host-level deferral applies policy filters); a narrow read-only search meta-tool (bounded query, optional namespace, maximum results; returns only approved immutable IDs and compact metadata; does not execute the found tool); domain subagents (a domain needing isolated context, its own tool set or budget; retrieval only within its eligible domain; propagate principal, tenant, purpose and policy version, not all parent credentials); grouped namespaces (one owner and policy domain each; no catch-all admin, utilities or everything namespace).

## 5. Reranking

- Choice: no reranker (the baseline of the reranking loop below). Use when: no candidate reranker improves the declared primary metric in that loop.
- Choice: cross-encoder reranker on the fused pool. Use when: first-stage recall is adequate but near-neighbour ordering is weak. Limits: pair the query with the intended effect, input contract, negative-use rule and workflow state; do not rerank the whole catalog; a generic passage reranker is not assumed to help tools.
- Choice: LLM reranker. Use when: a small pool where nuanced constraints, multi-tool coverage or pairwise comparison materially improve results. Limits: structured output with candidate IDs, rank, coverage reasons, missing prerequisites, ambiguity and abstention; IDs validated against the input set; catalog text isolated as untrusted data; not the authorization layer; prefer a cheaper deterministic reranker when quality is comparable.
- Choice: metadata-aware ranking after eligibility (health, latency, cost, freshness, verified past success, user preference) as tie-breakers. Limits: not raw call frequency; train only from verified outcomes and keep exploration for eligible new tools; rank a new tool from reviewed metadata, examples and neighbours, without penalizing missing history or promoting on synthetic outcomes.
- Reranking loop. Enter when first-stage recall passes but relevant tools sit below the exposure cutoff, or near-neighbour confusion exceeds the threshold. Freeze the pool and labels; score with reviewed fields only; compare NDCG, MRR, final-set recall, completeness, latency and cost against no reranker; check subgroups (rare, new, multilingual, multi-tool, high-risk tools); change one variable per variant. Exit when the primary metric improves without breaking recall, latency, cost or security gates; disable the reranker if it harms final-set recall or returns invalid IDs; stop after three unsuccessful variants and improve catalog text or first-stage retrieval.

## 6. Candidate budget

- Separate budgets for first-stage retrieval, reranking and final exposure. Starting ranges for a medium catalog (not standards; tune by task class, model, schema size, latency and risk; a smaller model may need fewer, more distinct tools, a complex multi-tool task more):
  - always-on core: three to eight universal, low-risk tools, only if evaluations show they are needed across most tasks;
  - first stage: 30 to 100 candidates per branch;
  - fused and deduplicated pool: 20 to 50;
  - exposed after reranking: five to twelve;
  - extra reserved slots for prerequisites, previously used tools and a required verifier.
- For an interactive task, default to at most three retrieval decisions, two query rewrites, two \(k\) escalations, and twelve unique exposed tools per decision; override only with a task-specific evaluated policy.
- Rules: keep a previously used tool while its result or handle is active, unless revoked, unhealthy or no longer authorized; add companion tools only after policy filtering; deduplicate aliases and versions by canonical ID; keep namespace-qualified names and deterministic order; diversify near-duplicates unless the ambiguity must be shown; reserve context for instructions, conversation, results, verification and the final response; escalate \(k\) only on evidence of a miss or low coverage.

## 7. Fallbacks and recovery

- Selection outcomes: the model selects only exposed IDs, asks for clarification, requests one bounded retrieval expansion with a reason, or abstains; validate that the selected tool and version were exposed and remain eligible.
- Empty or low-confidence result: distinguish empty eligible catalog, filter failure, index outage, true no-tool case and semantic miss; use a lexical-only or dense-only fallback only if preapproved and evaluated; check the always-on core; run the bounded rewrite and \(k\)-escalation loops; ask for clarification when user intent is the ambiguity; report capability unavailable rather than selecting a vaguely related tool.
- Search backend unavailable: a stale snapshot only within its age limit and after applying current revocation and entitlement data; high-risk tools fail closed.
- \(k\)-escalation loop. Enter when no candidate exceeds the confidence threshold, an uncovered subgoal or missing dependency is found, or a tool returns a deterministic wrong-capability error. Confirm the capability is not excluded by policy, lifecycle, health or compatibility; re-run with one controlled change (deeper branch, one query variant, an adjacent namespace, or validated graph edges); raise final \(k\) by a bounded step, such as five to ten, within the context-token ceiling; rerank and require coverage of each unresolved subgoal. Exits: an eligible candidate covers the need with margin; clarification when candidates imply different intents; capability unavailable when none appears. At most two escalations per decision and three retrieval rounds in total; do not widen into unauthorized namespaces.
- Rewrite and re-retrieval loop. Enter when no candidate passes the threshold, the top-score margin is below the ambiguity threshold, subgoal coverage is incomplete, or the model abstains for a missing capability. Diagnose the cause first (policy exclusion, stale index, poor query, small \(k\), missing dependency, unsupported capability, ambiguous request); never rewrite around a policy exclusion, return denial or capability unavailable; write one alternate query from the unresolved effect, inputs, outputs and negative constraints, keeping all user constraints; require improved coverage, margin or a new eligible tool. At most two rewrites and three retrieval rounds in total; stop earlier on a repeated candidate-set hash, the latency budget, or no measurable improvement.
- After a deterministic wrong-operation, unsupported-input or missing-prerequisite result with no side effect, retrieve once for the corrected subgoal; if a write may have occurred, reconcile before any retrieval or retry.

## 8. Index refresh

- Index build loop. Enter for the first index, a new embedding model or lexical analyzer, a schema change, or a full rebuild. Freeze catalog, policy schema, transformation and model versions; validate fields, uniqueness, namespaces, schemas, ownership and content limits, quarantining failures; build field documents, embeddings and postings with a source digest per item; verify counts, tenant partitions, absence of deleted items, vector dimensions and referential integrity; run smoke, offline retrieval, adversarial ranking and end-to-end tests. If a gate fails, change one major variable and rebuild; publish through an atomic alias only when every mandatory gate passes; stop after five failed build-evaluate iterations and revisit catalog quality or architecture.
- Incremental refresh loop. Enter on an approved catalog change, a protocol list-change notification (only a trigger), a health or entitlement change that alters visibility, a scheduled freshness deadline, or a staleness alert. Validate publisher, signature or digest, owner approval, schema and lifecycle transition; regenerate only affected documents and embeddings under the pinned pipeline; build a new immutable version or apply the delta with a completeness manifest; run affected-tool, near-neighbour, deleted-tool absence and regression tests; publish atomically and keep the previous version for rollback without letting a revoked tool through it. On failure keep the last known-good snapshot only for non-revoked tools, mark staleness, alert the owner and fail closed for uncertain high-risk tools; retry transient pipeline failures at most twice, then quarantine the change for an owner decision.
- Deletion or revocation: a synchronous deny by canonical ID and version. Publish the registry tombstone, block the tool in the policy layer and invocation denylist at once, remove every derived document, vector, alias, graph edge and cache entry, invalidate sessions that exposed it where the host permits, verify absence with exact-ID and semantic canary queries, and keep audit evidence without keeping the tool callable.
- Embedding model change: do not change it in place or mix incompatible vectors; build a new index through the build loop.
- Caches: cache only once eligibility inputs are known; recheck revocation, health and current entitlement on every hit; short time-to-live for policy- and health-sensitive results; bound negative-result caching so new tools become discoverable.
