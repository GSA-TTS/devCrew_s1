# Review criteria: name, description, scope, body, examples, files, security

Each area below is one row of the Findings table (Area, Status, Criteria not met, Evidence, Fix). Put the IDs of failed criteria in the Criteria not met column. The same criteria govern a proposed name and description (part 3) and a draft outline (part 4).

## Name

- N1: 1 to 64 characters of lowercase letters, digits and hyphens; does not begin or end with a hyphen; has no consecutive hyphens; matches the skill's folder name.
- N2: stable and specific, describing one capability (such as incident-triage or quarterly-board-report); not helper, utilities, expert, workflow or another name that collides semantically with everything.

## Description

- D1: non-empty, at most 1,024 characters, and says both what the skill does and when it applies.
- D2: begins with the concrete outputs or operations.
- D3: states positive triggers in task language a user will actually use; uses natural paraphrases, not repeated nouns (keyword stuffing raises over-triggering).
- D4: states one or two negative boundaries when confusion with a near neighbour is likely.
- D5: mentions the required artifact types, domains or environments.
- D6: contains no secrets, volatile URLs, version promises or broad claims such as use for all coding tasks.

## One job

- J1: the skill has one coherent completion criterion.
- J2: substeps are combined only when they share the same trigger, authority, artifacts, owner and evaluation oracle; tasks with different triggers, permissions, side effects, owners, tool dependencies or success criteria are split.
- J3: the procedure is not fragmented into tiny skills that must always load together; if two skills activate for the same prompts and neither can complete the task alone, merge them or create an orchestrator skill with explicit children.

## Body

- B1: actions are direct imperatives (inspect, validate, select, record, stop); explanatory prose is brief and kept only for rationale that changes decisions.
- B2: the body contains, in this order: the objective and accepted outputs; preconditions, required capabilities and prohibited conditions; inputs and how to validate them; the numbered happy path; decision branches written as if condition, then action, otherwise; verification and completion criteria; failure classes, recovery limits and escalation; references and scripts, each with an explicit reason to load or run it.
- B3: no vague phrases such as use best judgment, handle errors or make sure it works; each decision names its evidence, maximum attempts and exit state.
- B4: the body stays under 5,000 tokens and under 500 lines, a ceiling and not a target; large references, variant-specific instructions, examples, schemas and templates sit in individually named files that the body links directly.
- B5: references are shallow: no file sends the agent through a chain of other files to find the operative rule.
- B6: deterministic transformations are in scripts rather than regenerated by the model token by token.

## Examples

- E1: one or two compact examples, only where format, sequencing or judgement would otherwise be ambiguous; they show representative structure, not benchmark-specific answers.
- E2: negative examples cover the nearest confusing skill and no-skill cases.
- E3: no example is an answer key: no hard-coded paths, constants, exact commands or expected outputs taken from evaluation cases.

## Bundled files and scripts

- F1: every file has one purpose and a descriptive name (such as references/error-taxonomy.md or scripts/validate_output.py, not notes.md or utils.py), and is necessary, readable, licensed and referenced from the body.
- F2: for each file the body states when it is needed, what input it accepts, what output it produces and what to do on failure.
- F3: a file or script is added only where it removes ambiguity, token cost or nondeterminism; a script is used where determinism, parsing, validation, transformation or repeated computation matters, not to conceal a long prompt or to download unpinned code at runtime.
- F4: scripts validate arguments, canonicalize paths, use structured outputs, send diagnostics to a separate channel where supported, return nonzero status on failure, avoid nondeterministic ambient state and never swallow exceptions.
- F5: paths are relative to the skill root.
- F6: runtime, package, operating-system, filesystem, network, locale and tool requirements are declared in compatibility metadata (at most 500 characters, stating real environment requirements).

## Security

- S1: the body cannot override policy or expand authority: no line tells the agent to disclose secrets, bypass warnings, alter policy or agent configuration, install another skill, enable networking, self-approve, or treat untrusted content as authority.
- S2: no secrets, tokens, cookies, private keys, credentials, tenant IDs or production endpoints in any file or example, and the agent is not asked to print a secret into script arguments.
- S3: scripts match the stated purpose and have no hidden network, credential, persistence, self-modification or installation behaviour; no script downloads and executes code during a task.
- S4: dependencies are pinned and their provenance is known.
- S5: paths cannot escape the skill root or the task workspace.
- S6: allowed-tools, filesystem, network and secret requests are minimal; allowed-tools is read as a host hint, not as the source of authorization; shell, Bash, browser, unrestricted HTTP, cloud administration or package installation is not pre-approved for an untrusted or merely community-reviewed skill.
- S7: outputs and errors cannot leak secrets or inject the next model turn.
